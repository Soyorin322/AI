# Task 001 — Bootstrap Aiko / ai-friend Framework

## Objective

Bootstrap the first executable architecture skeleton for `ai-friend`, a generic modular framework for persistent AI characters.

This task is architecture-first.

The goal is NOT to implement Aiko's final Persona, Memory, Knowledge, Skill, Event, or Perception algorithms.

The goal is to create a clean, executable shell with stable subsystem contracts so later research results can be implemented without rewriting the whole project.

## Architecture requirements

### 1. Subsystem boundaries

Maintain separate modules for:

```text
character/
knowledge/
memory/
skills/
perception/
llm/
runtime/
```

A small shared `core/` or equivalent domain-contract module is allowed when it materially improves dependency direction.

Runtime is the coordinator.

Subsystems must not orchestrate each other.

Follow all dependency restrictions defined in `AGENTS.md`.

---

### 2. Explicit contracts

Define minimal typed public contracts for future replaceability.

At minimum provide abstractions equivalent to:

```python
CharacterProvider
KnowledgeStore
MemoryStore
SkillRegistry
PerceptionSource
LLMProvider
```

Use Python type hints throughout public APIs.

Prefer `Protocol`, ABCs, dataclasses, or similarly lightweight standard-library mechanisms.

Do not design final research-stage schemas.

---

### 3. Minimal domain models

Create only the minimum models required for the framework to operate.

Possible examples:

```text
CharacterIdentity
CharacterProfile / CharacterState
KnowledgeRecord
MemoryRecord
SkillDescriptor
PerceptionEvent
LLMRequest
LLMResponse
RuntimeContext
```

Names may differ if the existing repository already has reasonable equivalents.

Do not introduce detailed final models for:

```text
8-domain Persona
trait evolution
belief update
relationship evolution
emotion modeling
event cognition graphs
persona consolidation
skill proficiency
```

Those remain research-stage semantics unless the latest architecture document explicitly marks them ready for implementation.

---

### 4. Mock / in-memory implementations

For unresolved subsystems, implement simple replaceable versions only.

Examples:

```text
MockCharacterProvider
InMemoryKnowledgeStore
InMemoryMemoryStore
FilesystemSkillRegistry
MockPerceptionSource
MockLLMProvider
```

Do not introduce production frameworks merely to satisfy Task 001.

The architecture should make it possible to replace one implementation later without changing Runtime.

## Character


## Knowledge

Knowledge represents information available to the character.

Memory represents experience/history.

Keep them architecturally separate.

For Task 001, implement only a minimal in-memory KnowledgeStore with basic operations needed by tests/runtime, such as:

```text
add
get
search/list
```

Do not add:

- embeddings
- RAG
- vector search
- graph retrieval
- external knowledge services

---

## Memory

Implement the MemoryStore contract and a simple in-memory implementation.

A generic record should support at least:

```text
id
timestamp
content
metadata
```

Do not finalize the future Memory taxonomy in code.

Do not implement:

- consolidation
- forgetting
- summarization
- importance scoring
- persona-conditioned insight
- event graphs
- autonomous memory writing
- persona mutation

## Skills

Implement a generic Skill descriptor and registry.

Reserve support for filesystem skill packages such as:

```text
skills/
└── example_skill/
    ├── SKILL.md
    ├── scripts/
    ├── references/
    └── assets/
```

Only `SKILL.md` is required for the example.

The registry should be able to discover the example skill.

Do not implement tool execution or automatic skill creation yet.

---

## Perception

Define a typed event/observation abstraction that leaves room for:

```text
text
audio
screen
image
video
MIDI
system events
```

For Task 001, only text/mock behavior is required.

Do not implement actual microphone, screen capture, vision, video, or MIDI processing.

Perception must not directly mutate Character state.

---

## LLM

Define a provider abstraction equivalent to:

```python
generate(request) -> response
```

Create a deterministic mock implementation.

Do not integrate any real provider.

Runtime and domain logic must depend on the abstraction, not on the mock class.

---

## Runtime

Create or complete a central Runtime / Orchestrator.

Runtime should:

1. accept text input or a compatible PerceptionEvent;
2. obtain minimal character state;
3. obtain relevant mock/in-memory Knowledge and Memory context;
4. discover or expose available Skills;
5. build one explicit RuntimeContext;
6. pass an LLMRequest to the configured LLMProvider;
7. return the provider response.

Prompt/context composition must remain centralized rather than scattered across subsystems.

Do not implement advanced retrieval or context optimization yet.

---

## Executable demo

The project must support:

```bash
python -m ai_friend
```

Provide a minimal terminal loop such as:

```text
ai-friend generic runtime
Type "exit" to quit.

You > Hello
Example > Mock response to: Hello
```

The exact text may differ.

The response must travel through the actual Runtime and LLMProvider abstraction.

## Tests

Add focused tests that verify at minimum:
